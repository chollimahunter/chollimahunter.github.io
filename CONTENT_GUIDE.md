# Editing Chollima Hunter

This site is built so that almost everything — page wording, profiles,
hunt queries, IOCs, nav links, taxonomy tags — can be edited by changing a
plain text or JSON file, without touching HTML, CSS, or Nunjucks templates.
This guide covers the common edits. After editing a data file, run
`npm run validate` first: it checks enums, cross-file references and
normalized values in about a second, before anything is built. Then run
`npm run serve` to preview locally before pushing.

**The one rule that overrides everything else in this guide:** no factual
claim about a named, real individual may be published without at least
one citation to a real public record (DOJ indictment, OFAC sanction, court
filing, prosecutor's press release, or named threat-intel report) in that
entry's `sources[]` array. If you don't have a source, leave the field out —
don't guess, and don't invent a citation to fill a required field.

The site also publishes its own research alongside what it cites: values a
maintainer read directly off a live account or page, such as the records in
`src/_data/iocs/direct-observations.json`. These are labelled as the site's
own observation rather than attributed to a published source, and each cites
the page it was read from and the date it was read.

## Keep prose in paragraphs a reader will actually read

Several long-form fields render through the `paragraphs` filter, registered in
`.eleventy.js`. It accepts either a single string or an array of strings and
always yields a list, so any of these fields may be written either way:

- a hunt's `description` and `false_positive_notes`
- a profile's `disclaimer`
- a bulk dataset's `description`
- a taxonomy tag's `overview`, `tradecraft` and `defender_view`, which were
  already arrays

Write the field as an array once it runs past roughly 90 words, with one array
element per paragraph. A single 300-word string renders as one unbroken block
that nobody reads to the end, however well sourced it is. Aim for 40 to 90
words per paragraph and break where the subject genuinely shifts, such as from
what a technique does to how a defender sees it, or from one vendor's reporting
to another's.

The exception is a verbatim quotation. `wanted_details.caution`, `remarks` and
`reward` are transcribed from a law-enforcement notice and stay as single
strings, unedited, however long they run. They render inside a blockquote, so a
reader can see that the length is the agency's rather than this site's.

## Change page wording

The prose pages — Home and EtherHiding Tracker — are plain **Markdown**
files, not HTML:

| Page | File |
|---|---|
| Home | `src/index.md` |
| About DPRK (section of Home) | `src/index.md` |
| EtherHiding Tracker | `src/etherhiding/index.md` |

Open the file and edit the text like a normal document — headings start
with `#`/`##`, bold is `**text**`, links are `[text](/url/)`, lists start
with `-`. A few things in each file are wrapped in raw HTML on purpose
(`<section>` tags for spacing/styling, `<div class="disclaimer-banner">`
for warning boxes, `<h2 id="...">` for headings other pages link to by
anchor) — leave those tags in place, just edit the text between them.

The other pages (DPRK Hunting, DPRK Profiles, Repo Scanning Tool, Submit
IOC/Profile, and the two results pages) are `.njk` templates because they
render data-driven tables and loops, not fixed prose. Their wording (intro
paragraphs, form labels, disclaimer text) can still be hand-edited directly
in the file — just be careful not to touch the `{% %}` / `{{ }}` template
logic.

## Add a new hunt (DPRK Hunting page)

Edit `src/_data/hunts/hunts.json` — it's a JSON array; add a new object to
it. Each entry becomes both a tile in the grid at `/hunts/` and a page of
its own at `/hunts/{id}/`, generated by `src/hunts/hunt-page.njk` through
`src/_includes/layouts/hunt.njk`. No template needs editing to add a hunt.

```json
{
  "id": "your-hunt-id-kebab-case",
  "title": "Short human-readable title",
  "hunt_type": "TTP Hunt",
  "summary": "One or two sentences. This is all the grid tile shows, so it has to stand alone.",
  "description": "What this hunt detects and WHY it matters, in prose.",
  "technique_scope": "The technique this targets, ideally with a MITRE ATT&CK technique ID.",
  "campaign_tags": ["Contagious Interview"],
  "data_sources": ["EDR process telemetry", "Proxy/DNS logs"],
  "indicators": [
    { "type": "Domain", "value": "example.com", "note": "What it is and which source reports it." }
  ],
  "queries": [
    {
      "platform": "Defender / Sentinel KQL",
      "language": "kql",
      "origin": "authored",
      "source": "Publisher name",
      "query": "DeviceProcessEvents
| where ..."
    }
  ],
  "confidence_level": "medium",
  "false_positive_notes": "What legitimate activity also triggers this, and how to tune it out.",
  "sources": [
    { "title": "Report title", "url": "https://...", "publisher": "Publisher name", "date": "2026-01-01" }
  ],
  "last_updated": "2026-08-30"
}
```

`hunt_type` is one of `IOC Hunt`, `TTP Hunt` or `Behavioral Hunt`. An IOC
hunt matches atomic values a report published (addresses, domains, hashes,
package names); a TTP hunt matches the behaviour, tooling or artefacts of a
technique regardless of the specific values, which covers malware and
hardware alike; a behavioural hunt is statistical, looking for a pattern
across sessions or records rather than any single event. It becomes a badge
on the tile and a filter chip on the library page; the chips are derived
from the data, so a new value creates its own chip with no template change,
but keep to the three above so the filter stays meaningful. When hunts are
merged, add the retired id to `src/_data/hunts/redirects.json` so the old
address still resolves. The same is true of
`platform` on a query.

`indicators` is optional. Where it is present it renders as a table above
the queries, so someone can lift the values into tooling that speaks none
of the query languages. Every value in it must be reported by one of the
entries in that hunt's `sources[]`.

**Query provenance is not optional.** Every query carries an `origin`:

- `"reproduced"` — the query is published by the cited source and appears
  exactly as that source wrote it. Do not tidy, reformat or "improve" it;
  if it needs changing, it is an authored query that credits the source's
  indicators instead.
- `"authored"` — written for this site against indicators the cited sources
  document. Only write a query in a language you can write correctly.
  Inventing plausible-looking syntax for a platform is worse than omitting
  it, because a reader cannot tell the difference.

Set `source` to the publication, and add `source_url` to link the
provenance line straight to the article. **Credit publications, never
individual authors** — use the site or vendor name (`Grumpy Goose Labs`,
`mattysplo.it`, `ReliaQuest`), not a byline.

### Validating a query before you publish it

Do not publish a query in a language you cannot check. Most of them can be
verified mechanically, and it is worth doing — a rule that does not compile is
worse than no rule, because a reader cannot tell the difference from the page.

```bash
pip install pysigma pysigma-backend-splunk yara-python
```

- **Sigma** — parse and compile every rule, then run the rule validators:
  `SigmaCollection.from_yaml(text)` to parse, `SplunkBackend().convert(...)` to
  prove it compiles, and `sigma.validators.core` for rule-quality checks.
  Compiling against a second backend (`pysigma-backend-kusto` with the
  Microsoft XDR pipeline) is a useful cross-check, but note that backend does
  not support correlation rules and has no table for the Windows Security log
  or for proxy logs, so failures there are not necessarily rule defects.
- **YARA** — `yara.compile(source=...)`, then `.match()` against a short byte
  string so the rule is proven to run, not merely to parse.
- **osquery** — the queries are SQLite. Create a table with the columns from
  <https://osquery.io/schema/>, run the statement against it, and check the
  rows are what you expected.
- **PowerShell** — `[System.Management.Automation.Language.Parser]::ParseFile()`
  reports syntax errors without executing anything. Parsing is necessary but
  not sufficient: a pipeline broken before its script block still parses and
  then fails at runtime.
- **KQL, SPL, XQL, LogScale** — no local validator, so check each operator and
  function against the vendor's own reference. Two traps worth knowing: KQL's
  `has` family matches whole terms and will not match a substring of a longer
  word, and Splunk allows wildcards in an `IN` list under `search` but not
  under `where`.

`platform` is the display label and the filter chip, so keep it short and
reuse an existing one where the language is the same. Current values:
`Sigma`, `Splunk SPL`, `Defender / Sentinel KQL`, `CrowdStrike Falcon`,
`Cortex XQL`, `Elastic`, `osquery`, `PowerShell`, `Shell`,
`Shodan / Censys`, `YARA`.

A hunt may carry more than one query for the same platform — the tile
de-duplicates the chips.

## Add a new IOC (Repo Scanning Tool ruleset)

Edit `src/_data/iocs/repo-scan-ruleset.json` — a JSON array, same pattern.

```json
{
  "id": "your-ioc-id-kebab-case",
  "ioc_type": "npm_package",
  "value": "the-literal-indicator-value",
  "campaign": ["Contagious Interview"],
  "description": "What this indicator is and what matching it signals.",
  "malware_family": "BeaverTail",
  "confidence_level": "high",
  "sources": [
    { "title": "Report title", "url": "https://...", "publisher": "Vendor name", "date": "2026-01-01" }
  ],
  "date_added": "2026-08-15"
}
```

`ioc_type` must be one of: `npm_package`, `pypi_package`, `file_hash`,
`filename`, `domain`, `hosted_site`, `payload_url`, `ip_address`, `asn`, `github_dork`,
`smart_contract_address`, `transaction_hash`, `wallet_address`, `ens_name`,
`c2_pattern`, `chrome_extension`, `malicious_repository`,
`compromised_repository`, `email_address`, `github_profile`,
`linkedin_profile`, `personal_site`, `phone_number`, `skype_account`,
`username`, `alias`, or one of the platform-account types in
`PLATFORM_ACCOUNTS` in `scripts/lib/ioc-normalize.js` (`telegram_account`,
`x_account`, `medium_account`, `gitlab_account`, `devto_account`,
`freelancer_account`, `codesandbox_account`, `dockerhub_account`,
`keybase_account`, `huggingface_account`, `trello_account`, `quora_account`,
`odnoklassniki_account`, `freelancermap_account`, `fiverr_account`,
`upwork_account`, `laborx_account`, `klimbup_account`, `peerlist_account`, `xing_account`,
`torre_account`, `himalayas_account`, `producthunt_account`, `f6s_account`,
`entre_account`, `linktree_account`, `remoteok_account`, `remotehub_account`,
`balkanfreelance_account`, `wantedly_account`, `hashnode_account`,
`calendly_account`, `instagram_account`, `facebook_account`,
`stackoverflow_account`, `useme_account`, `cryptojobslist_account`,
`web3career_account`, `cryptojobs_account`, `devpost_account`,
`youtube_account`, `discord_account`; the table in that
file is the authority when this list lags). If you
can't find a real, citable public report for an indicator, don't add it — an
uncited IOC is a liability, not a lead.

An entry whose cited reporting does not tie it firmly to North Korea (a
report that names another actor, or none, for infrastructure that shares
DPRK tooling) carries `attribution_doubt`: one or two sentences saying what
the reporting does say. The maintainer ruled on 2026-10-11 that such entries
are tracked with the doubt marked rather than left out. The indicator page
and the EtherHiding Tracker show a "DPRK link unconfirmed" badge with that
text, and the page's opening sentence says "tracked as possibly North Korean"
rather than "attributed".

A `payload_url` is a full URL on a shared paste or JSON-bin service (or any
host a report's indicator table types as a malicious URL), written as
`https://jsonkeeper.com/b/4NAKK`: lowercase scheme and host, the path as
printed, no fragment. The host alone is not an indicator, so a bare host is
refused by `normalizePayloadUrl`. It is always rendered as text and never as a
link.

Every type in that list except `github_dork` and `c2_pattern` also appears in
the indicator index, with its own `/indicators/{id}/` page — those two are
search queries and detection patterns rather than identifiers a defender looks
up, so `src/_data/iocIndex.js` filters them out.

Write an `email_address` as the mailbox it reaches, not as the sender typed it —
for Gmail only. Google ignores dots in the local part and everything after a
plus, and serves googlemail.com as gmail.com, so
`a.l.l.a.nh.orca0.7@googlemail.com` and `allanhorca07@gmail.com` are one mailbox
and must be one record; `normalizeEmail` reduces both to the second. Dotting is
deliberate in this corpus — at the time this normalizer was introduced, several
hundred of the Gmail addresses in the index carried a dot and several were the
same mailbox sprayed differently in each report — so this is the difference
between one indicator and a dozen. Everywhere else a dot is an
ordinary character: `a.smith@outlook.com` and `asmith@outlook.com` are two
people's mailboxes, and Outlook, Proton and Yahoo addresses are stored exactly as
written. The same rule applies to a submission that arrives through
`/submit/`: normalize a Gmail address before filing it, leave every other host
alone. Where the source printed something other than the mailbox, keep what it
printed in `display`, which the page shows as "Listed as" and the search matches
against.

Write a `phone_number` in E.164 and nothing else: `+18327063757`, never
`(832) 706-3757` or `832-706-3757`. A record's id is a hash of its value, so the
same line written three ways is three indicators with a third of the citations
each — which is what had happened to 419-746-0450 before `normalizePhone` in
`scripts/lib/ioc-normalize.js` started canonicalizing it. A dossier entry is run
through that normalizer at build time and a number it cannot place stops the
build, so a value with no country code has to be a ten-digit NANP number; write
the country code out for anything else.

A bulk dataset of package indicators is the one exception, and it has rules of
its own: entries must be version-pinned (`name@version`), because for a
compromised legitimate package the bare name identifies the victim rather than
the threat, and the dataset's `disclaimer` is carried onto every record it
produces so a bulk entry never renders as a bare value beside a campaign chip.
See `src/_data/iocs/osm-malicious-package-versions.json` for the shape and
`docs/osm-mining.md` for the reasoning.

**Package and extension indicators belong here, not in the scraper.** Automated
extraction cannot reliably tell a malicious package from the legitimate one it
impersonates, or a malicious extension from the wallet it targets. An entry
added to this file is human-verified and renders with the strongest provenance
badge on the index. See `docs/scrape-dprk-iocs.md` for the full reasoning.

## Add a new EtherHiding watchlist entry

Same shape as above, in `src/_data/iocs/etherhiding-watchlist.json`, using
`ioc_type: "smart_contract_address"` or `"c2_pattern"`. Never invent a
plausible-looking contract address — if you don't have one from a cited
report, leave the watchlist as-is until one is published. The same rule covers
addresses that are real but not indicators: a researcher's own demonstration
contract from a write-up of the technique does not belong in a watchlist of
DPRK infrastructure.

A `c2_pattern` entry may also carry an optional `detection` block, which is
what lets `scripts/check-etherhiding-contracts.js` apply the pattern
mechanically instead of leaving it for a human to read. Its literal strings
must come from what the cited report specifies and nothing more. The field
reference is in `docs/etherhiding-contract-check.md`; an entry without the
block still renders normally and is reported as unevaluated by the checker.

## Add a new DPRK actor profile

Add one new JSON file to `src/profiles/` — the filename (minus `.json`)
becomes the URL slug, and the page is generated automatically. No other
file needs to change.

```json
{
  "slug": "your-slug",
  "display_name": "Full Name",
  "aliases": ["Alias One", "Alias Two"],
  "confidence_level": "confirmed",
  "cluster_taxonomy": ["Lazarus Group"],
  "personas": [],
  "emails": [],
  "phone_numbers": [],
  "github_repos": [],
  "photo_slot": { "image_path": null, "caption": "", "source": "" },
  "fake_ids": [],
  "sources": [
    { "title": "Report or record title", "url": "https://...", "publisher": "DOJ / OFAC / vendor name", "date": "2026-01-01", "type": "indictment" }
  ],
  "disclaimer": "All claims on this profile are drawn exclusively from the cited public records in the Sources section below.",
  "last_updated": "2026-08-15"
}
```

Rules that matter here specifically:
- **Every field you populate must trace back to a source in `sources[]`.** Leave a field out (empty array / null / omitted) rather than guess — an empty `emails: []` is normal and expected if no public record specifies one.
- `confidence_level` must be `confirmed` (named in a charging document or wanted notice from a law-enforcement agency, in a guilty plea, conviction or sentence announced by the prosecuting authority, or in a government sanctions designation, whether by OFAC or by the Republic of Korea's Ministry of Foreign Affairs and Financial Services Commission), `high`, `medium`, or `low` — matching how the *source itself* characterizes the attribution, not your own judgment call.
- A source's `type` is one of `indictment`, `court_filing`, `wanted_notice`, `sanctions_designation`, `press_release` or `reference`. A `press_release` from the prosecuting authority announcing a guilty plea, conviction or sentence supports `confirmed` on its own.
- `cluster_taxonomy` values must exactly match a `label` in `src/_data/taxonomy.json` (see below) — that's what makes the tag link to the right spot on the About page.
- `photo_slot.image_path` should stay `null` unless you have a verified public-record image. Never add a stock/placeholder photo. If the source publishes a photograph this site does not mirror, leave `image_path` null and write a `caption` plus a `source` URL — the layout then says so and links out rather than claiming no image exists.

### Required when a profile has a photograph: `name_korean`

Any profile whose `photo_slot.image_path` is set must also set `name_korean`.
**The build fails if it does not** — see the `eleventy.before` check in
`.eleventy.js`. A portrait without the Hangul reads as a half-finished entry,
and it is easy to add one and forget the other.

A profile whose subject is not a DPRK national has no Korean rendering to
publish, and inventing one would be worse than leaving it out. Those profiles
set `name_korean_not_applicable` to a short reason instead, which satisfies the
build check and records the decision on the page's data rather than leaving an
unexplained gap:

```json
"name_korean_not_applicable": "United States citizen and domestic facilitator rather than a DPRK national, so no Korean rendering of the name applies."
```

Where the Hangul comes from a source that publishes it (the FBI's
Korean-language poster covers the fourteen DPRK IT Workers), set
`"name_korean_provenance": "cited"` and add that source to `sources[]`. Where it
is the conventional rendering of the romanized name rather than a sourced
spelling, set `"name_korean_provenance": "reconstructed"` — the profile page
then says so beneath the name. Romanization is lossy in both directions, so do
not present a reconstruction as if a source published it.

### Optional: `wanted_details`

Profiles drawn from a law-enforcement wanted notice carry a `wanted_details`
object holding what the notice itself publishes, transcribed rather than
summarized:

```json
"wanted_details": {
  "status": "Wanted by the FBI; listed under Cyber's Most Wanted",
  "details": [
    { "label": "Hair", "value": "Black" },
    { "label": "Nationality", "value": "North Korean" }
  ],
  "caution": "Full Caution text, quoted verbatim from the notice.",
  "remarks": "Full Remarks text.",
  "reward": "Full Reward text.",
  "field_offices": "St. Louis",
  "related_cases": [{ "title": "DPRK IT FRAUD", "url": "https://..." }],
  "poster_url": "https://www.fbi.gov/wanted/cyber/<slug>/@@download.pdf"
}
```

`details` is an ordered label/value list rather than fixed keys on purpose:
notices differ in which fields they publish, and the layout renders whatever is
present without needing to know the vocabulary in advance.

A profile whose record is a sanctions designation rather than a wanted notice
uses the same block for what OFAC's entry publishes, and sets `heading` to
"Sanctions-designation details" so the section is not mislabelled; the
default heading is "Wanted-notice details". A profile drawn only from an
indictment or a court record, with no wanted notice or designation, sets
`heading` to "Court-record details", which the eleven facilitator profiles use. Where a person has both, as with
the Sobaeksu designees who also carry a State Department reward notice, the
default heading stands and `caution` quotes the Treasury press release while
`remarks` quotes the notice.

Quote `caution`, `remarks` and `reward` in full and unedited. The agency's own
wording is the claim this site repeats; paraphrasing it puts the paraphrase
beyond what the citation supports. Omit any field the notice does not publish.

## Add or edit an actor-cluster taxonomy tag

Edit `src/_data/taxonomy.json` — one place, used by the Home page's cluster
grid, every profile page's cluster-tag links, *and* the cluster page generated
for each entry at `/clusters/{id}/`. You don't need to touch anything else.

```json
{
  "id": "your-anchor-id",
  "label": "Exact Label Used In Profiles",
  "description": "One or two sentences explaining this cluster.",
  "also_known_as": ["Other vendors' names for the same activity"],
  "indicator_campaigns": ["Campaign label as it appears on indicators"],
  "hunt_tags": ["Campaign tag as it appears on hunts"],
  "overview": ["What this cluster actually does.", "Second paragraph."],
  "tradecraft": ["How it differs from the other clusters on this site."],
  "defender_view": ["What a defender would see if they were hit by it."],
  "further_reading": [
    { "title": "Report title", "url": "https://...", "publisher": "Publisher", "date": "2026-01-01", "note": "One line on what this one is good for." }
  ]
}
```

The `id` is both the anchor on the Home page (`/#your-anchor-id`) and the URL
segment of the cluster page (`/clusters/your-anchor-id/`); the `label` is what
must be typed verbatim into a profile's `cluster_taxonomy` array for the link
to resolve correctly.

Only `id`, `label` and `description` are required. Everything else feeds the
cluster page, which is generated by `src/clusters/cluster-page.njk` through
`src/_includes/layouts/cluster.njk` from `src/_data/clusters.js` — that file
joins the tag to the profiles, personas, indicators, hunts and citations the
site already holds, so no count or list on a cluster page is ever written by
hand.

Two of the fields are join keys rather than prose, and setting them wrongly
mislabels a whole page:

- `indicator_campaigns` must match `campaign` values carried by indicators in
  the index. The distinct values currently in use across `src/_data/iocs/` are
  `APT37`, `APT38`, `Andariel`, `Contagious Interview`, `Contagious Trader`,
  `DPRK (cluster unattributed)`, `EtherHiding`, `IT Worker Fraud`, `Kimsuky`,
  `Konni`, `Lazarus Group`, `Moonstone Sleet`, `NullReceiver`, `PolinRider` and
  `UNC5342`. In `src/_data/taxonomy.json`, most clusters carry a single
  matching campaign (`lazarus-group` → `Lazarus Group`, `apt38` → `APT38`,
  `kimsuky` → `Kimsuky`, `andariel` → `Andariel`, `apt37` → `APT37`,
  `konni` → `Konni`, `moonstone-sleet` → `Moonstone Sleet`, `polinrider` →
  `PolinRider`); `contagious-interview` carries both `IT Worker Fraud` and
  `Contagious Interview`, and `rgb-reconnaissance-general-bureau` carries all
  of the APT-cluster labels plus those two. `Contagious Trader`,
  `DPRK (cluster unattributed)`, `EtherHiding`, `NullReceiver` and `UNC5342`
  are not yet mapped to a cluster tag. It scopes the cluster page's indicator
  search and its type-filter counts. An empty array means the page states
  plainly that the index holds nothing under this cluster, which is the
  correct outcome for a tag the site holds only charging records for — do not
  invent a campaign label to fill it.
- `hunt_tags` must match `campaign_tags` values in
  `src/_data/hunts/hunts.json`. A hunt matches if it carries *any* of them, so
  the two broad tags `DPRK IT Worker Fraud` and `Contagious Interview` are
  enough to pick up every hunt in the library.

The three prose fields are arrays of paragraphs and are rendered as HTML, so a
paragraph can carry a link (`<a href="/hunts/">…</a>`) into the rest of the
site. Write them the way the rest of the site is written: formal, third-person,
and specific enough that a reader who already knows the general shape of DPRK
operations learns something. Keep derived numbers out of the prose — the page
renders its own counts, and a figure typed into a paragraph goes stale the next
time a data file changes.

`further_reading` is a curated recommendation list, not a link dump. Draw
entries from reporting the site already knows about — `src/_data/iocs/scrape-sources.json`,
the cached source documents under `_drafts/iocs/`, and the `sources[]` arrays
on the relevant profiles — verify every URL resolves before adding it, and give
each one a `note` saying what that report in particular is good for.

## Add an entry to the observable-indicator register

The register on `/remote-workers/red-flags/` is `src/_data/tradecraft.json`:
a `sources` map keyed by a short id (each entry a `url`, `title`,
`publisher` and the short `label` the table shows), then `categories[]`,
each with a `name` and its `indicators[]`, then `priorities`, the legend
the page prints above the table: what priority 1, 2 and 3 mean. Every
indicator carries `indicator` (the one line the row is filed under),
`detail` (rendered small underneath), `priority` (1, 2 or 3, shown as a
P1 to P3 badge) and `sources[]`, which are keys into the map at the top
rather than source objects. Adding a key there is what puts the citation on
`/sources/`. Two fields are optional: `hunts[]`, ids of hunts under
`/hunts/` that look for the observation, and `link`, an `{ "href",
"label" }` pair pointing at a page on this site, such as an indicator or a
search. The reports carry the explanation; the row links to them rather than
paraphrasing.

The selection rule matters more than the schema. A register of everything
one of these operations touches is mostly ordinary software, and a row for
Zoom or an applicant tracking system is true and useless because every
legitimate candidate uses the same things. An entry earns its place when
the observation is difficult to account for innocently: a hardware KVM on a
company laptop, a virtual camera answering an identity check, a
multi-factor secret generated in a browser. An observation that is common on
its own but counts alongside others is priority 3; if the honest reason for a
row would read "lots of people do this" and nothing more, it belongs in the
behavioural list above the register, or nowhere.

## Add or reorder a nav link

Edit `src/_data/nav.json` — an array of `{ "label": ..., "url": ... }`
objects, rendered in order in the header nav.

## Site-wide config (site URL, contact email, Ko-fi link)

Edit `src/_data/site.json`. `url` feeds the canonical links, Open Graph
tags, sitemap and feed, so it must match where the site is actually served.
`repoUrl` feeds the footer's source link and every "open an issue" link, and
is left empty while the repository is private: each of those links renders
only when it is set, and the licence is served from the site as
`/license.txt` either way. `businessEmail` is the contact address; change it
there and nowhere else, since every template reads from this one file,
including the `/submit/` page's `mailto:` link. If it is ever emptied or
set to a placeholder containing `TODO`, the site degrades rather than
breaks: the submission page is replaced by a notice, the footer and About
page show no contact link, and `/.well-known/security.txt` is not written.
`indexNowKey` is the key `scripts/indexnow-submit.js` sends with each
IndexNow submission and the build publishes as `/{key}.txt` so the search
engines can verify it (see `docs/search-indexing.md`); changing it takes
effect on the next deploy.

## Design / colors / spacing

All visual styling lives in one file: `src/assets/css/tokens.css`. Colors,
spacing, fonts, and glow/shadow effects are defined as CSS custom
properties (`--accent`, `--background`, `--muted-foreground`, `--radius-lg`,
etc.) at the top of the file — change a value there and it updates
everywhere that token is used, rather than hunting through every page.
Fonts are self-hosted from `src/assets/fonts/` (see that folder's
`LICENSE-fonts.txt`) — no external font CDN.

## Which page an indicator is searchable on: the `area` field

`src/_data/iocIndex.js` tags every record with an `area` after the merge, and
that tag decides which page searches it. There are four values.
`etherhiding` covers the on-chain infrastructure in
`etherhiding-watchlist.json`, searched on `/etherhiding/`. `polinrider` covers
the compromised-repository list in `polinrider-affected-repos.json`, searched
on `/repo-scanner/` together with the repo-scan ruleset entries, which stay
in the remote-worker index as well, and also on `/remote-workers/`, where
they appear under the compromised repository type (the cluster pages and the
home page search leave them out). A compromised repository is stored as
`owner/repo`, shown everywhere as the full `https://github.com/owner/repo`
text (the `iocLabel` filter and `displayValue()` in `ioc-search.js`), and
never rendered as a link. `espionage` covers a record whose only
`campaign` values are pure intrusion or heist clusters — Lazarus Group,
Kimsuky, APT37, Konni, APT38, Andariel, Moonstone Sleet, or unattributed
DPRK — searched from that cluster's own page under `/clusters/`; see the
`ESPIONAGE_CAMPAIGNS` set in `iocIndex.js` for the exact rule and why a
record that also carries an IT-worker campaign tag stays out of it.
Everything else is `remote-workers`.

The split is by indicator kind rather than by campaign for `etherhiding` and
`polinrider`, and the reason is the same in both cases: those two sets name
what was attacked, not who ran the attack, and there are enough of them to
swamp an identity index by count while answering a different question.
`espionage` is the one split by campaign, for the same reason of count and
subject: an APT intrusion indicator answers a different question from an
operator's own identity. Records in every area keep their own
`/indicators/{id}/` page and still count toward their citation on `/sources/`,
so nothing is hidden, only filed where it answers something.

If you add a bulk dataset of victims rather than of operators, give it an area
of its own the same way, and state the exclusion on `/remote-workers/` rather
than letting it be silent.

## Add a new bulk IT-worker identifier dataset (Profiles → "IT Worker Identifiers" tab)

This is a different pattern from a single profile: it's for a **bulk list**
(tens to thousands of entries) ingested wholesale from one report, where
every entry shares the same source citation — hence the separate shape
below rather than reusing the single-indicator IOC pattern.

Push a new object into the array in
`src/_data/iocs/itworker-datasets.json`:

```json
{
  "dataset_id": "your-source-slug",
  "title": "Dataset title as named by its source",
  "ioc_type": "email_address",
  "campaign": ["IT Worker Fraud"],
  "confidence_level": "low",
  "description": "What this dataset is and how the source says it was compiled.",
  "disclaimer": "The source's own caveats about false positives / unverified attribution, carried forward near-verbatim.",
  "source": { "title": "...", "url": "https://...", "publisher": "...", "date": "2026-01-01", "type": "threat_intel_report" },
  "entry_count": 0,
  "entries": []
}
```

The `src/remote-workers/index.njk` template already loops over every
dataset in this file — a new dataset object appears on the page
automatically, no template change needed.

**If the source has a live page you can keep in sync automatically**
(like DTEX's advisory), write a sibling script to
`scripts/sync-dtex-itworker-emails.js`
(fetch → extract → validate → diff → write the dataset object in place)
and add a matching job to
`.github/workflows/sync-itworker-datasets.yml`. That workflow runs weekly
and opens a **pull request** — never a direct commit — when the fetched
list differs from what's checked in, so a human reviews new/removed
identifiers before they go live. `entry_count` must always equal
`entries.length` exactly; a sync script that overwrites the whole dataset
object each run (rather than hand-patching fields) keeps this true
automatically.

## Add a source to the indicator scraper

Push an entry into `sources[]` in `src/_data/iocs/scrape-sources.json`:

```json
{
  "url": "https://vendor.example/research/report",
  "publisher": "Vendor name",
  "campaign": ["IT Worker Fraud"]
}
```

`campaign` is the DPRK activity cluster the source reports on. Sources
currently carry `APT37`, `APT38`, `Andariel`, `Contagious Interview`,
`DPRK (cluster unattributed)`, `EtherHiding`, `IT Worker Fraud`, `Kimsuky`,
`Konni`, `Lazarus Group`, `Moonstone Sleet`, `NullReceiver` and `PolinRider`,
and a source may carry more than one. `npm run validate` accepts no other
label: those, plus `EtherHiding / UNC5342`, which is what the index shows for a
source tagged `EtherHiding` or `UNC5342`. A new label goes into a cluster's
`indicator_campaigns` in `src/_data/taxonomy.json` first. It is applied to every indicator drawn
from that source and becomes a filter chip on `/remote-workers/`. Set it
deliberately: a report often name-checks several clusters while reporting on
one, and the wrong value mislabels every indicator that source contributes.

Adding a host here also excludes it (and its subdomains) from extraction, so the
report's own navigation, author bios and footer links never become indicators.

A source may also carry `exclude`, a list of `{ "value", "reason" }` pairs
naming values the page prints that are not indicators -- a compromised
maintainer's account in a mitigation command, a profile the report lists
without saying whose it is. The value is dropped at extraction and again on
ingest, and the reason is the record of why. Use it for one value in one
report; a pattern that recurs across reports belongs in
`scripts/lib/ioc-normalize.js` as a rule. Then run `npm run seal`: the
readable pair moves to the maintainer's private checkout and the public file
keeps only `{ "sealed": "<hash>" }`, because an excluded value usually belongs
to someone uninvolved. `npm run validate` fails while an entry is unsealed.
`scripts/data/false-positives.json` works the same way.

Then run `node scripts/scrape-dprk-iocs.js --source <url>` followed by
`node scripts/ingest-scraped-iocs.js`, and **read the staged output** before
committing. See `docs/scrape-dprk-iocs.md`.

### Sources that were evaluated and rejected

`not_scraped[]` in the same file records every URL that has been checked and
turned down, with a `reason` and the date checked. Add to it rather than
discarding the finding — it is what stops a future review spending an afternoon
re-confirming that a site renders client-side or that a URL 404s. Reasons in use:
`blocked`, `client-side-rendered`, `dead-url`, `declined`, `held-for-decision`,
`indicators-in-hrefs-only`, `link-hub`, `no-campaign-named`, `no-dprk-keyword`,
`no-extractable-indicators`, `rate-limited`, `transcribed-by-hand`,
`withdrawn`.

---

If the source has no accessible public list (narrative/guidance only,
gated behind a form, or a PDF that can't be reliably parsed) — don't
invent entries to fill the gap. Document it as reviewed-but-not-seedable
instead, the way DTEX vs. Microsoft's Jasper Sleet reporting is handled in
`sync-dtex-itworker-emails.md`.

## Submissions from the public

Incoming submissions (via the `/submit/` mailto page) are never
auto-published. Turn one into a draft using the process documented at
`docs/submission-review-assist.md`, which writes
a reviewable draft to `_drafts/profiles/` or `_drafts/iocs/` — you then
manually promote it into `src/profiles/` or the relevant `_data/iocs/*.json`
file using the templates above once it's sourced and verified.
